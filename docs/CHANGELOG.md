# JARVIS 更新日志

## v1.0.5 (2026-10-24) 多轮对话：第二轮之后不再"听着就没下文"

现象：第一轮问答正常，接着说第二个指令时界面走到「思考 → 聆听」，然后一直挂着，
既不报错也不出结果。多轮只能撑一到两轮。

### 根因：麦克风比人慢了 1.8 秒

旧逻辑里，一轮回答播完之后要满足「出声状态完全回落 + 连续静默 1200ms」才算说完，
再叠 600ms 尾音缓冲才轮到开麦 —— **播报收音之后还要 1.8 秒麦克风才打开**。
而真人的行为就是"它一停我就开口"，于是第二句整句落在麦克风关着的窗口里，
循环这才姗姗到达录音状态，只录到一片空白，白等两轮后退出了会话。

后端日志把这一点钉死了（同一段连续对话）：

```
第一轮 → 14 帧裁到 8 帧 → 识别「按系统时区来」        ✅
第二轮 → 24 帧 idle=True（整段没到说话门槛）         ❌
第三轮 → 20 帧 idle=True                          ❌
重新喊唤醒词
第四轮 → 20 帧裁到 9 帧 → 识别「查询湖北荆州的天气」   ✅
第五轮 → 24 帧 idle=True                          ❌
```

帧数是满的（6.6 秒 ÷ 256ms ≈ 24 帧），说明麦克风一直在跑，只是那段没人说话。

### 修复

1. **喊唤醒词即刻开麦**（主修复）：命中唤醒词时，如果会话循环还在"等回答播完"，
   不再丢掉这次命中，而是立刻中断等待去把麦克风交出去。
   同时把静默判定 `1200ms → 500ms`、尾音缓冲 `600ms → 250ms`。
2. **会话看门狗**：加心跳与"会话世代"。循环若卡死超过 25 秒（例如某个请求没回来），
   下一次唤醒会掐断它在途的请求并另起新一代接管 —— 以前那种情况会**永久静默失效**。
3. **唤醒词剥离**：真人习惯"喊唤醒词 → 停顿 → 说指令"，而端点检测恰好在停顿处判停，
   于是喂给模型的常常只剩一句「你好贾维斯」。现在会把开头那句唤醒词剥掉；
   剥完为空就再听一轮，而不是把唤醒词当提问发出去。
4. `/record/stop` 支持中断信号；自己还在播报时开不了麦不再算作"用户没理它"
   （以前这种情况会让会话在自己播报期间就提前退出）。

### 附带：麦克风改成进程内唯一一条流

旧实现每录一次就新建一个 PyAudio 实例、**对同一个设备 open 两条流**（第一条只用来
试探能不能打开，成功就再也不关），录完在后台线程 `terminate()`，而两轮之间只隔
14 毫秒。现改为一次打开、长期运行，录音只是挂个监听者；没人听之后自动关闭。

> 注明疗效归属：这一项修的是确凿的资源泄漏与潜在的生命周期竞态，但真机对照测试
> 没能复现"第二轮变哑"（安静环境下两种写法电平一致），所以它**不是**上面这个
> 用户问题的主因。真正的修复是上面 1–4。

VAD 状态机也从闭包抽成 `VadCollector` 类以便单测；录音日志现在会带上
「峰值电平 / 说话门槛 / 判停原因」，以后不用再猜是麦克风哑了还是人没开口。

### 顺带修好

两个数据库（`jarvis.db`、`data/chroma_db/chroma.sqlite3`）出现 SQLite
`disk I/O error`（只读），已用 dump + 重建的方式恢复，数据完好
（99 个会话 / 543 条消息）。

## v1.0.4 (2026-10-24) 唤醒引擎换到 Vosk 受限语法

这一版解决的是「喊了没反应」——**不是麦克风坏了，是唤醒模型认不出这台机器的声音**。

### 根因：sherpa 3.3M KWS 在这台阵列麦上只有 8% 召回

- 麦克风、音频链路、语音识别全部正常：实时录音送 Paraformer，能一字不差识别成「你好贾维斯」
- 但同一段音频送 sherpa-onnx 的 3.3M zipformer KWS，**真实人声 26 段只命中 2 段（8%）**
- 频谱对比给出了答案（历史能命中的样本 vs 实时录音）：

  | 频段 | 历史样本 | 实时录音 | 差异 |
  |---|---|---|---|
  | 0–200Hz | 0.350 | 0.441 | 低频偏多 |
  | **500–1000Hz** | **0.422** | **0.190** | **少了 55%** |
  | 1000–2000Hz | 0.069 | 0.037 | 少 46% |

  元音共振峰区被掏空，频谱呈「两头翘、中间凹」

- 决定性对照实验：把历史样本**从扬声器播出来再录回来**（音质更差）反而能命中 → 麦克风与路径是忠实的，差异在信号本身
- 排除清单（逐项有数据）：音量（增益扫到削顶也不中）、boost/门限（2.0 与 10.0 结果完全一致，说明模型是"自信地判错"而非灵敏度不足）、9 种滤波/预加重组合、生产封装层 bug、拼音 token 错误、3 秒切片切断唤醒词、通道选错

### 换引擎：Vosk + 受限语法

- **方案**：完整 LVCSR 声学模型 + 把解码器搜索空间锁死在唤醒词上的受限语法。等效于"只让模型在几条路径里挑最像的那条"，容错度远高于端到端小模型
- **实测**（26 段真实人声 + 24 段环境噪声，全部经 ASR 复核）：

  | 方案 | 召回 | 误报 | 响应 |
  |---|---|---|---|
  | sherpa 3.3M KWS | 8% | 0% | — |
  | **Vosk small + 单字语法** | **73%** | **0%** | 1.58s |
  | Vosk cn-0.22 大模型 | 50% | 0% | 2.23s |

  小模型反而更好：大模型为通用识别优化，语法受限场景不划算

- **两个必须记住的坑**：
  1. 中文语法必须写成**单字序列**。直接传「你好贾维斯」整词，Vosk 只打一行
     `Ignoring word missing in vocabulary` 然后静默失效，表现为 0 命中且无任何报错
  2. 语法里必须留 `[unk]` 出口，否则环境噪声会被强行解码成唤醒词
- 语法含 20 条：基准词 + 单字同音替换变体 + 只喊名字的「贾维斯」
- 静默期自动复位解码器（连续 40 次检查无中间结果），防止噪声在 lattice 里堆成唤醒词
- 三个引擎并存，`JARVIS_WAKE_ENGINE=vosk|sherpa|porcupine|energy` 切换，默认 vosk
- 前端修掉一处会让 Vosk 起不来的判定：`needsKey` 原先写成 `engine !== "sherpa"`，
  Vosk 会被误判成"需要 Picovoice 密钥"而永不启动。改成只认 porcupine

### 评估方法上的两个教训

- **误报率必须先用 ASR 复核再下结论**：一度统计出 14% 误报，逐片复核后发现那 4 片
  全是轻声说的真唤醒词，实际误报 0%
- **别靠用户卡时间喊**。改用扬声器回放做麦克风通道 A/B：同一段音频播放、
  逐通道录制，声学输入完全相同，结论才可靠且不折腾人

### 采集方式：改用回调模式，不再用阻塞 read()（本轮最关键的收获）

- 同一台机器、同一时刻、同一条通道的对比：

  | 读法 | rms | peak | 直流 |
  |---|---|---|---|
  | 阻塞 read(1024) | 0.14162 | **1.0000** | +0.02390 |
  | 阻塞 read(512)（生产原用法）| 0.03987 | **1.0000** | +0.00109 |
  | 回调 1024 帧/次 | 0.00378 | 0.0244 | -0.00007 |
  | 回调 512 帧/次 | 0.00540 | 0.0460 | -0.00026 |

- 阻塞 read 拿回来的信号**恒为满刻度削顶**并带直流偏置。原因是驱动缓冲溢出时
  PortAudio 默认把样本**钳位**到 ±32767 而不是丢弃。削顶会注入大量谐波，
  等于把唤醒模型的输入直接污染掉 —— 这与「频谱中频被掏空」互为表里
- 改成回调模式：PortAudio 用自己的线程按驱动节奏取数，不溢出。回调里只入队，
  主循环从队列取（超时 0.25s 以便干净退出）。生产路径实测 peak 从 1.0 降到 0.002
- 麦克风探测 `_measure` 也一并改了：此前它测的是削顶后的假电平（动辄 0.29），
  送到诊断面板上是自欺欺人
- 阈值随之下调：`SILENT_RMS` 0.002 → 0.0005。原值是阻塞 read 时代的遗留——
  那时电平虚高，阈值只能跟着虚高，结果**安静房间里的好通道会被误判成死通道**
  并触发无谓的换通道。`ALIVE_RMS` 0.004 → 0.008，避免排序被本底噪声牵着走

### 播报自激 / 多轮串音 / 响应慢：播报期间没把耳朵闭上

- **现象**：播报过程中把自己的声音回传、多轮对话一两轮后就分不清是在
  思考还是收音、回答前还要干等一两秒。
- **根因**：三者同源——**播报期间麦克风没闭**。日志实证：
  `11:31:36 chat/stream` → `11:31:45.06 record/start` → `11:31:45.10 /tts 返回`，
  即「播报还没开始，录音已经开了」，自己的声音被完整录入，VAD 误判 →
  连续 idle → 退出会话。前端只看 `isPlaying` 判不了这段：字节到浏览器才
  置位，"流完 → 合成 1.8s → 才播"的空档里它是 false。
- **修复·三层防线**：
  1. 新增服务端出声锁 `app/output_lock.py`——TTS 一发出就上锁（音频时长
     +0.8s 回声余量），`/record/start` 锁内等待，唤醒引擎锁内丢帧并复位
     识别器。前端状态是主防线，这把锁是不依赖浏览器时序的兜底。
  2. 前端统一「在出声」信号 `voice.speaking`（合成中 + 播放中），唤醒挂起、
     会话开麦、等回答结束三处全部改看它。
  3. 延迟：改成**分句流式播报**——LLM 每吐出完整一句就立刻合成播放，
     首句出声时间从"整段生成完"提前到"第一句生成完"。
- MP3 时长估算不能按 128kbps 反推（实测算 18s 实际 7s），改用语速为主。

### 唤醒后进不了对话：VAD 录音也在吃削顶音频

- **现象**：唤醒命中（后端日志有「唤醒命中 score=0.80」），服务端录音也
  一轮轮在跑，但每轮都 idle 结束——「说话门槛>=1.0595」永远达不到。
- **根因**：VAD 录音循环（`/api/voice/record/start`）与按钮录音
  （`_record_blocking`）仍在用**阻塞式 `stream.read()`**。本机阵列麦驱动在
  阻塞读法下返回削顶音频（peak 恒 1.0、RMS 虚高近 10 倍），VAD 拿这种
  底噪标定出 1.06 的说话门槛——正常说话（0.02~0.1）永远够不到，于是
  「唤醒成功但怎么都进不了对话」。
- **修复**：两处采集全部改为 **PyAudio 回调模式**（与唤醒引擎同款修法）。
  标定值恢复「说话>=0.0100 静音<0.0060」，20 帧 ≈ 5.1s 与真实时间同步。

### 麦克风选择：改为按宿主 API 优先，不再只比电平

- 只比电平不可靠：**安静环境下好通道与死通道读到的都是 ~0.0005 的底噪，
  直接比电平等于比谁的本底噪声大**。实测同一台机器上一会儿选中 device 5
  （rms 0.077）、一会儿选中 device 1（rms 0.0005），而 device 1 是坏的
- 真正稳定的判据是宿主 API。扬声器回放同一段音频的实测：

  | 通道 | API | 回放 rms |
  |---|---|---|
  | 0 声音映射器 | MME | 0.0010（死）|
  | 1 麦克风阵列（系统默认）| MME | 0.0010（死）|
  | 4 主声音捕获驱动程序 | DirectSound | 0.0992（可用）|
  | 5 麦克风阵列 | DirectSound | 0.0997（可用）|

- 排序改为 WASAPI > DirectSound > WDM-KS > MME；电平**只在确实听到声音时
  （≥ 0.004）才参与比较**，安静时一律按 0 处理
- 修正一处错误排除：「主声音捕获驱动程序」原先被当成 MME 聚合通道排掉了，
  但回放实测它能真采集（0.0992）。现保留使用，只是排在直接命名的通道之后
  （它转发的是系统默认设备，默认设备一变它的输出跟着变）。真正该排的是
  「声音映射器」（0.0010，死）
- 连测 4 次稳定选中 device 5

## v1.0.3 (2026-10-14)

### 语音唤醒：说完了就走，且能连续对话

- **指令采集改用 VAD，不再傻等固定窗口**：原先命中唤醒词后固定录 4 秒（没听清再补 2.5 秒），说完话也得干等窗口走完。现在 `/api/voice/record/start` 支持 `{"vad": true}`，检测到人声后连续静音 700 毫秒即自动停录并转写；`/record/stop` 在 VAD 模式下语义变为「等说完再转写」（手动截断传 `immediate`），不传 `vad` 时行为与旧版完全一致。**喊完到出字从 6 秒以上压到说完约 1~2 秒**
- **连续对话**：唤醒一次即进入会话模式，每轮回答播完自动开麦听下一句，不必重新喊唤醒词；连续两轮没人说话自动退回待唤醒——与小爱同学一致。判定「回答播完」要求连续 1.2 秒既不忙也不播，用以跨过流结束到 TTS 起播之间 200–800 毫秒的合成空档，否则会把上一句尾音录成新指令
- **唤醒开关默认开启**：唤醒是主入口，不该每次先点开关；关掉过会记住（localStorage `jarvis.wake`）。此前默认是关的
- **修掉一个让唤醒彻底失效的判据**：前端启动监听前校验 `access_key_set`，这是 Porcupine 时代的规则；sherpa 是免密钥引擎，该值恒为假，于是前端认定引擎未就绪、**连启动都不调**，且不报错，表现为「开了开关也没反应」。现在按引擎分流，后端对 sherpa 直接视为就绪

### 指令识别：换成中文 Paraformer

- **唤醒后的指令不再交给 Vosk 转写**。Vosk 的 `vosk-model-small-cn` 是老一代 Kaldi 模型，实测把「你好贾维斯」识别成「你好 假 微丝」，长句错得更厉害——这正是"它听得见我，但听不懂我在说什么"的根源。现在改由 sherpa-onnx 的中文 Paraformer 识别（新一代非自回归模型），**复用唤醒引擎已有的运行时，不引入任何新依赖**
- **实测对比**（本机，同一段音频）：真实录音「你好贾维斯」——Paraformer **1.28 秒、完全正确**，Vosk 2.57 秒、识别成「你好 假 微丝」；合成长句「帮我把今天的日程安排念一遍，顺便提醒我下午三点开会」——Paraformer **1.35 秒全对**，Vosk 3.35 秒（字对但慢 2.5 倍）。可用 `scripts/dev/compare_stt.py` 复现
- **三档回落**：Paraformer（中文首选）→ faster-whisper（混语种）→ Vosk（兜底）。任一档不可用都静默降级，不会让语音链路断掉
- **非 16kHz 音频自动重采样**：Paraformer 只在 16kHz 上训练，喂别的采样率不会报错、只会输出一堆错字，属于最难排查的静默降级，已在入口显式处理
- **模型目录靠扫描而不是拼路径**：目录名带日期版本号（`sherpa-onnx-paraformer-zh-small-2024-03-09`），写死必然在换模型后失效。`scripts/dev/download_paraformer_asr.py` 负责下载（默认 78MB 的 small 版，可选 228MB 标准版），`JARVIS_ASR_MODEL_DIR` 可指定目录
- **下载器改成多段并行**：本机单连接只有约 26KB/s，78MB 要下近一小时；实测同一文件开多段并发能到约 126KB/s（瓶颈在单连接限速而非总带宽）。分段各自续传，中断重跑不丢进度。另外加了**停滞检测**：服务端会用"极慢但不间断"的方式吊着连接，光靠 socket 超时抓不到（实测有一段就这么卡了 13 分钟），现在 45 秒没有新字节就断线重连

### 采集与识别的两个真机坑

- **VAD 阈值改为按底噪动态推导**。原先写死 0.006，而本机安静环境的底噪 RMS 实测 **0.00496**——两者几乎贴在一起，环境稍有动静就被判定为"一直在说话"，结果录满 8 秒上限才停。现在每次录音先采几帧环境声估计底噪，阈值取底噪的 2~3 倍并设下限，说话与静音两个阈值之间留迟滞
- **识别前先裁掉首尾静音**。原因是识别模型在大段静音上会**产生幻觉**：实测 Paraformer 对一段含长静音的音频输出过「多名成员帮我把今天的日程安排念一遍高志正选人上台后首位因丑闻辞职的歌了此时距离」这种胡话，而接口照样返回 200，只有跑一次才知道错了。现在 VAD 模式下只把检测到人声的那一段（前后各留 200/300 毫秒）送去识别；整段都没人声则直接判为空闲、根本不调模型

### 语音播报

- **在线合成失败自动落本地**：edge-tts 调微软在线接口返回 403 时，整条播报链路静默失效（表现为「AI 回答了但一句话都听不见」）。现在 `app/tts.py` 增加 Windows SAPI 本地兜底，在线优先、失败自动落本地，`JARVIS_TTS_ENGINE=auto|edge|sapi` 可切。本机可用语音为 Huihui（中文）、Zira（英文）

### 启动器与采集通道（09:00 补充）

- **日志里的关键证据**：`Recording stopped: 26.2s, rms=0.00268` + `Recording is silent (mic may be muted)`。这不是模型问题，是**麦克风送进来的就是静音**
- **逐设备实测（干净环境下）**：系统默认通道 device 1 rms **0.003**，另一条同名通道 device 5 rms **0.05~0.59**（差两个数量级）。之前自动选麦里"默认设备够响就提前收工"的快速路径，会被 device 1 的底噪波动（0.0008 ~ 0.006）骗过，从而选中死通道 —— **已删掉该快速路径，改为把候选全探完再取电平最高的**
- **排除 MME 聚合通道**：「Microsoft 声音映射器 - Input」「主声音捕获驱动程序」自己不采集，只是转发到系统默认设备；默认设备若是死通道，它们跟着一起死，还会搅乱探测结果
- **修掉日志整行丢失**：设备名里的 ® 在 GBK 控制台/重定向下会抛 `UnicodeEncodeError`，导致那条日志**一行都写不出来**。`启动贾维斯.bat` 现在设置 `PYTHONUTF8=1`，代码侧也做了安全转义
- **堵住引擎被重复启动**：前端的两个订阅循环会先后各调一次 `/start`，而采集线程是**异步**才把状态置成 listening，只靠 `status` 判断会同时起两个引擎、开两条麦克风流。加了 `_starting` 标记（并在采集线程出口用 finally 复位，避免"一次异常永久失效"）

### 麦克风：自动挑一条真正有声音的通道（本轮真正的元凶）

- **不再信任系统默认输入设备**。Windows 上同一块硬件会暴露多个 endpoint，默认的那个常常「打得开、`read()` 也不报错，但读出来全是数字静音」。本机实测：默认通道（设备 1，英特尔智音阵列）RMS **0.00085**，另一条同名通道（设备 5）RMS **0.0195**。程序只要跟着默认走，症状就是**功能全对、日志全绿、状态是 listening、电平事件也在推，但用户怎么喊都不唤醒**——因为送进模型的从头到尾都是静音。这正是"改了很多版却一点变化都没有"的成因，且它不以任何异常的形式出现
- **新增 `app/mic_selector.py`**：逐条探测候选通道的实际电平再选。跳过回环设备（名字含 output/输出/混音 的抓的是系统播放声，选到它会让播报把自己唤醒）；默认通道有正常底噪时走快速路径、不逐条探测；结果缓存 5 分钟。探测会先丢掉开头 300 毫秒——阵列麦刚打开时读到的是纯 0，直接拿来算会把好通道误判成死通道
- **静音看门狗**：监听期间持续盯电平，整整 8 秒连环境底噪都没有就判定该通道失效，自动换下一条重试（最多 3 次），并把失效通道拉黑 10 分钟。全部试完仍然没声音时**明确报错**「麦克风没有收到任何声音」并给出排查路径（Windows 设置 → 隐私和安全性 → 麦克风），而不是继续假装 listening
- **录音与唤醒共用同一条通道**：`/api/voice/record/start` 与 `/mic-check` 此前都用系统默认设备，会出现「唤醒监听有声音、按按钮录音没声音」这种自相矛盾的现象，现在统一走 `mic_selector`
- **诊断信息外露**：`/api/wakeword/info` 增加 `device_resolved`、`device_name`、`mic_rms`、`mic_silent`。光有设备下标说明不了问题，必须把实测电平一起给出来，用户才能在界面上一眼区分「引擎没起来」和「麦克风根本没声音」
- **实测**：修复前引擎 `peak_level` 恒为 **0.001**，按按钮录 26 秒日志直接告警 `Recording is silent (rms=0.00268)`；修复后自动选中设备 5，`peak_level` 达到 **0.34**，`/mic-check` 返回 `heard_sound: true`

### 启动器：残留进程会把新代码挡在外面

- **`启动贾维斯.bat` 启动前先清理上一轮残留**（electron.exe 与占用 18200 / 5173 的进程）。关掉窗口只是缩到托盘，后端和前端并不会退出；以前启动时看到端口被占用就跳过并复用，结果用户明明换了新代码，界面和接口却还是**前一天那个没退干净的旧进程**——同样表现为"一点变化都没有"
- **桌面端加单实例锁**：之前每次双击都会再开一个实例，桌面上可能同时挂着新旧两个窗口。现在第二个实例直接退出，让已在运行的那个重新加载前端并弹到前台

## v1.0.2 (2026-10-13)

### 语音唤醒重构

- **替换轮询式伪唤醒**：原实现为「录 3 秒 → 停 → 通用语音识别 → 正则匹配文本」，延迟不低于 3 秒，且常把唤醒词切在窗口边界整体丢失。改为 sherpa-onnx 开放词表关键词检测（Zipformer 3.3M / WenetSpeech 中文 / int8），流式判定，端到端反馈压到 300 毫秒内
- **换唤醒词不再需要训练**：改用开放词表方案后，「你好贾维斯」只是唤醒词文件里的一行文本，改完即时生效，不需要重新训练模型、不需要任何账号或密钥。原先为纠正误识别的「假为为师」热词补丁表与音近正则一并移除
- **唤醒词改成「中文源 + 编译产物」两份文件**：模型是拼音建模的，直接写汉字不会报错、只会永远检测不到。现在 `keywords_raw.txt`（一行一个中文词，入库，给人改）由 `scripts/dev/build_sherpa_keywords.py` 编译成 `keywords.txt`（`n ǐ h ǎo j iǎ w éi s ī :2.0 @你好贾维斯`）；后端启动时检测到中文源更新会自动重编。改唤醒词的完整动作只剩「编辑中文源 + 跑一条命令」
- **为什么不是 Porcupine**：原定方案为 Picovoice Porcupine，但其 Console 注册需要邮箱验证，而官方已确认验证邮件会被收件方邮件服务器隔离，实际注册无法完成。Porcupine 代码保留为 legacy，将来拿到 AccessKey 可切换回
- **唤醒不再依赖语音识别**：旧链路用通用模型识别「贾维斯」再做文本匹配，是「叫不应」与「乱答应」的共同根因。新链路关键词引擎只负责判定一个词，准确率与响应速度都不再受识别模型质量牵连
- **事件驱动推送**：后端 `/api/wakeword/stream` 由 500 毫秒轮询改为事件队列推送，新增设备管理、灵敏度调节、热重载、暂停恢复、离线回放测试、误唤醒留证等端点
- **唤醒诊断面板**：设置页新增语音唤醒分组，提供灵敏度调节、麦克风选择、实时电平、环境自检，以及误唤醒录音的回放与打标
- **打包不再静默失效**：`backend.spec` 显式收集 sherpa-onnx 的原生库（DLL 由 `sherpa-onnx-core` 提供，必须与主包同版本）与模型目录，并在状态接口暴露自检字段，缺少任何一个文件都能立刻定位
- **查明了本机 onnxruntime 的历史加载故障**：`C:\Windows\System32` 与 `SysWOW64` 下各有一份游离的 `onnxruntime.dll`（版本 1.17.2606.1301），Windows 按模块名解析依赖时会命中它，这正是过去 `onnxruntime` 升到 1.27 就加载失败的根因。实测确认 sherpa-onnx 不受影响（其 .pyd 优先加载自己目录下的那份），因此**没有改动系统目录**
- **修掉两个只在真机上暴露的问题**：清理音频流的 API 是 `reset_stream(stream)` 而不是 `reset()`，写错要到命中那一刻才崩（单测替身已同步改名）；模型压缩包里的文件名带训练配置后缀（`...-chunk-16-left-64.int8.onnx`），所有定位模型文件的地方改为 glob 匹配且 int8 优先
- **新增两个验证脚本**：`verify_sherpa_offline.py` 无人值守跑离线回放（模型自带 7 条负样本断言不误报 + SAPI 合成唤醒词断言能命中，本机实测全绿）；`build_sherpa_keywords.py` 编译并预览唤醒词的拼音 token

### 已知限制

- 唤醒之后的指令识别仍走既有链路，仍可能识别错字。语音识别引擎升级列为后续独立项，本次未包含
