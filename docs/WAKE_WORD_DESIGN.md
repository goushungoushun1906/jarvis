# JARVIS 语音唤醒 · v2「你好贾维斯」方案设计

> 目标：**响应够快、叫得应、不乱答应**，体验对标小爱同学 / 小艺。
> 设计优先级：**响应速度 > 准确率 > CPU 占用**（CPU 不作约束）。
> 实现分支：`feat/wakeword-v2`。

---

## 0. 为什么要重做

旧实现并不是真正的"关键词检测"，而是"识别之后再猜"，路径如下：

```
录 3 秒 → 停止 → 通用语音识别 → 拿文本 → 正则找「贾维斯」
```

对应代码是 `src/hooks/useWakeWord.ts` 里的 `LISTEN_WINDOW_MS = 3000` 循环，以及后端 `app/stt.py` 的热词纠错表。这套做法有五个结构性问题：

| 症状 | 位置 | 根因 |
| --- | --- | --- |
| 喊完要干等好几秒 | `useWakeWord.ts:32` | 窗口必须录满才交付，端到端延迟不低于 3 秒 |
| 有时完全叫不应 | 同上 | 唤醒词常被切在两个录音窗口的边界，整句丢失 |
| 需要堆音近匹配 | `useWakeWord.ts:26-27` | 通用识别把「贾维斯」稳定听成「假为为师」，只能靠正则兜：`[贾假讲加家甲嘉佳][维为微威唯委伟]*(?:斯\|丝\|师\|思\|司\|私\|狮)`，排列组合爆炸 |
| 播放语音时完全听不见 | `useWakeWord.ts:165` | 为避免听到自己的声音，干脆整轮跳过监听，因而无法打断 |
| 三套实现互相打架 | `app/wakeword.py`、`useSpeechRecognition.ts`、`useWakeWord.ts` | 后端那套 Porcupine 实现从未被前端接入 |

**结论：调参救不回来，必须换架构。**

## 1. 新架构

手机助手之所以"秒响应且不乱叫"，是因为唤醒根本不经过语音识别，而是由**只认识一个词的专用模型**做逐帧判定。新链路如下：

```mermaid
flowchart LR
    A["麦克风常驻采集<br/>16k / 单声道 / 32ms 每帧"] --> B["Porcupine 中文关键词引擎<br/>逐帧判定，无需凑够窗口"]
    B -- "未命中" --> A
    B -- "命中" --> C["事件队列 → SSE<br/>毫秒级推到前端"]
    C --> D["前端：打断播报 + 视觉反馈<br/>已在 300ms 内"]
    D --> E["开麦采集指令 → 语音识别 → 对话"]
```

关键差异：**关键词引擎只负责一个词**（模型几十 KB，对这个词极度敏感），而**通用识别负责一万个词**（对这个音译词毫无先验）。用后者做唤醒，是拿错了工具。

由此带来的连锁简化：**唤醒判定不再走语音识别**，"假为为师"这个 bug 从根上消失，`stt.py` 的热词补丁表可以整段删除。

| N8 | 语音播报走云端合成、浏览器播放，后端拿不到播放状态 | `tts.py`、`useAudioPlayer.ts` | "是否正在播放"的真值源在前端，后端只能被动接收暂停与恢复通知 |
| N9 | 前端六态状态机与 HUD 内部状态存在编译期同构断言 | `types.ts:235-243`、`JarvisHud.tsx:37-39` | 不新增第七态，"已唤醒"继续复用"聆听"，额外视觉走独立属性 |

## 2.1 引擎换血：Porcupine → sherpa-onnx

### 为什么换

原方案选 Picovoice Porcupine，**卡死在注册环节**：Console 注册后需要邮箱验证，
而官方 issue #70 已确认「验证邮件会被收件方邮件服务器隔离」。实际使用代理邮箱
注册时验证邮件始终收不到，整条链路无法推进。

替代方案评估：

| 方案 | 换词成本 | 账号依赖 | 结论 |
| --- | --- | --- | --- |
| **sherpa-onnx 开放词表 KWS** | **改一行文本，免训练** | 无 | **选定** |
| openWakeWord | 每个唤醒词都要合成数据重新训练 | 无 | 成本高，作为备选 |
| Porcupine | Console 网页训练后下载 .ppn | 需要 AccessKey | 注册不通 |

**sherpa-onnx 的开放词表**是决定性优势：模型本质是一个微型 ASR（Zipformer
3.3M 参数，WenetSpeech 中文语料训练，int8 仅数 MB），解码时只允许输出你指定的
关键词。**换唤醒词 = 改一行文本，不用重新训练模型**，而且打包后用户改词也能
立即生效。

### 关键词是拼音建模的，不能直接写汉字

踩到的第一个坑：这份模型的建模单元是**拼音（声母 + 韵母 + 声调）**，喂给
`KeywordSpotter` 的关键词文件里必须是拼音 token，写汉字不会报错、只会永远
检测不到 —— 典型的静默失败。所以唤醒词有两份文件：

| 文件 | 内容 | 谁改 |
| --- | --- | --- |
| `keywords_raw.txt` | `你好贾维斯`（一行一个中文词） | 人，**唯一真源**，入库 |
| `keywords.txt` | `n ǐ h ǎo j iǎ w éi s ī :2.0 @你好贾维斯` | 编译产物，sherpa 读 |

编译链路（`app/wakeword.py`）：`pinyin_tokens()` 用 pypinyin 拿到**书写形式**的
音节（jun / xue / wei），按正字法切出声母韵母，再从 `tokens.txt` 反查带调写法。

两个细节决定了这条链路能不能用：

1. **不能用 pypinyin 的 `FINALS`**。它给的是音理上的韵母（wéi → `uei`、
   jūn → `ǖn`），与模型词表的书写形式（`w + éi`、`j + ūn`）对不上，照搬会整条
   词条 OOV。模型自带样本把「你好问问」写成 `w èn`，说明它按正字法切。
2. **声调符号不能自己拼**。pypinyin 会把 wéi 写成 `ueí`（调号标错位置），
   所以改为从 `tokens.txt` 反推 `{（无调韵母, 声调号）: 带调写法}` 这张表，
   保证产物一定在词表里。

pypinyin 只在**改词之后**第一次启动用到，产物已是最新时整条链路不碰它，因此
只进 dev 依赖、不进生产依赖。改词的完整动作：

```bash
# 编辑 server/models/wakeword/sherpa-onnx-kws-*/keywords_raw.txt
python scripts/dev/build_sherpa_keywords.py      # 编译并预览 token
```

### 实测结论：System32 的游离 DLL 没有造成阻塞

这是本次最大的意外收获。原以为会踩 k2-fsa/sherpa-onnx#3059 那个坑，实测结果
**相反**（见 `scripts/dev/verify_sherpa_dll.py`）：

```
先加载 pip 的 onnxruntime 1.26.0（模拟 chromadb 抢先加载）
再导入 sherpa_onnx → 报告 1.28.2

进程内实际加载的两份 DLL：
  site-packages\onnxruntime\capi\onnxruntime_providers_shared.dll   ← 1.26.0
  site-packages\sherpa_onnx\lib\onnxruntime.dll                     ← 1.28.2

C:\Windows\System32\onnxruntime.dll   ← 未出现
```

原因是 Windows 解析 .pyd 依赖时，**被加载模块自身所在目录**的优先级高于
System32。所以**不需要改动系统目录**——原本准备让用户做的「把 System32 那份
DLL 改名」这一步可以省掉（那是唯一有系统级副作用的方案）。

保险起见仍在 `app/sherpa_runtime.py` 里做了应用级兜底（`os.add_dll_directory`
在 import 之前注册），并在体检面板暴露 `stray_system32_onnxruntime`，万一将来
出问题能一眼看见根因。

### 两个引擎的语义差异（最容易搞错）

| 维度 | Porcupine | sherpa-onnx |
| --- | --- | --- |
| 调用方式 | 逐帧 `process(pcm)` | 流式 `accept_waveform` → `decode_stream` |
| 返回值 | 关键词下标 `int` | 关键词字符串 `str` |
| 置信度 | 无 | 无（仍只能用阶梯推导） |
| 灵敏度方向 | **越大越易触发** | 阈值**越小越易触发** |
| 换词成本 | 重新训练下载 .ppn | 改一行文本 |

方向相反这一条尤其危险，因此在引擎层做了单调递减映射
（`threshold_from_sensitivity`），让配置与前端始终只面对「灵敏度」一种语义，
前端滑杆零改动。

### 保留 Porcupine

`pvporcupine==4.0.3` 在 requirements 里标为 legacy 但保留。将来若拿到
AccessKey，`JARVIS_WAKE_ENGINE=porcupine` 即可切回，代码路径完整可用。

## 3. 各层设计要点

### 3.1 后端服务（`server/app/wakeword.py`）

以 `WakeEngine` 协议抽象出引擎层，将来换开源引擎只需实现同一份协议，编排层不动。

| 项 | 设计 |
| --- | --- |
| 多唤醒词 | 一个引擎实例可同时监听多个关键词，返回的即是命中下标，官方保证无额外运行时开销 |
| 密钥读取 | 旧实现在模块导入时读一次环境变量，之后改配置不生效。改为每次调用重读，并支持密钥热重载，无需重启后端 |
| 灵敏度热调 | 调整灵敏度时不关闭麦克风流，只重建引擎实例，用户拖动滑杆即时生效 |
| 线程模型 | 单一采集线程负责读帧，通过线程安全回调扇出到事件队列；慢订阅者丢弃最旧事件，绝不阻塞音频采集 |
| 无需预滚缓冲 | 关键词引擎是逐帧流式状态机，命中帧即词结束帧，不存在"开头几个字节被吃掉"的问题。保留环形缓冲是为了另一件事：误唤醒留证 |
| 与手动录音解耦 | 唤醒不再占用全局录音单例，与按住说话的功能互不干扰 |
| 降级策略 | 拿不到密钥时**不再降级到能量检测**。旧的那套会把任何说话都当成唤醒，比没有唤醒更糟；改为明确报错并引导去填密钥 |

**自检字段**是防"打包后静默失效"的关键：状态接口直接暴露原生库是否存在、中文参数是否存在、关键词文件是否存在、资源目录是否存在。以往这类问题表现为"没反应但也不报错"，排查成本极高。

### 3.2 接口层（`server/app/routes/wakeword.py`）

由 500 毫秒轮询改为事件推送。心跳使用注释帧而非数据帧，否则前端的帧解析器会产出无法解析的负载。

| 能力 | 说明 |
| --- | --- |
| 设备枚举 | 列出可用输入设备并标记可能的系统内置麦克风。此前项目没有任何设备选择能力 |
| 灵敏度调节 | 运行时生效，不中断采集 |
| 暂停 / 恢复 | 播报与手动录音期间暂停判定但不关闭音频流，避免设备独占冲突 |
| 离线回放测试 | 上传音频走一遍判定，**不占用麦克风**，用于验证打包产物是否正常 |
| 误唤醒留证 | 每次命中保存前 1.5 秒音频，支持回放、下载与打标。只保留最近若干条，可在设置中关闭 |

### 3.3 前端（`src/hooks/useWakeWord.ts` 等）

- 从"循环录音"改为订阅事件流，复用项目已有的 SSE 帧解析器
- 保留原有的阶段类型与返回值形状，避免牵动其他 UI
- 断开时指数退避重连，重连后重新拉取引擎状态校正，防止后端已经换了引擎而前端还停留在旧状态
- **三层防自激**：后端冷却时间 + 前端唤醒守卫 600 毫秒 + 应用层暂停通知。守卫过渡时间比默认更长，是为了留出语音播报的尾音与扬声器回声
- 兜底快捷键：开关唤醒、强制开麦。保证引擎异常、麦克风权限异常时用户仍有可用路径

#### 3.3.1 VAD 采集：说完就停，不再傻等固定窗口

命中唤醒词之后要采集的是**指令**，它的长度完全由用户决定——一句话可能
2 秒，也可能 8 秒。最初的实现是固定录 4 秒、没听清再补录 2.5 秒，代价是
说完还得干等窗口走完，端到端"喊完到出字"要 6 秒以上，这是"对话不流畅"
的直接来源。

现在 `/api/voice/record/start` 支持 `{"vad": true}`：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `silence_ms` | 700 | 检测到人声后，连续静音这么久即判定"说完了"，自动停录 |
| `max_ms` | 8000 | 单次采集硬上限，防失控 |
| `min_ms` | 600 | 开始说话后的最短录音时长，防一个喷麦音就截断 |
| `leading_ms` | 5000 | 一直在等、始终没人开口的放弃时长 |

判定门槛 `_VAD_SPEECH_RMS = 0.006`，比"麦克风是否被禁用"的
`_SILENCE_RMS = 0.004` 略高一层：说话是持续能量，这样可以把偶尔的敲键盘
挡在"说话"之外。

配套地，`/record/stop` 在 VAD 模式下语义变成**"等说完再转写"**：自动停发生
在录音线程里，stop 轮询等待（上限 10 秒）后照常转写；要手动截断就传
`{"immediate": true}`。**不传 `vad` 时行为与旧版完全一致**，按钮路径不受影响。

一个容易搞错的细节：VAD 等满 `leading_ms` 也没等到人声时，返回
`{"text": "", "idle": true}` 而**不带 `error`**。这是连续对话的正常空闲退出，
若错报成"麦克风故障"，前端会把"用户没理它"渲染成一场事故。

#### 3.3.2 连续对话：唤醒一次，说到不想说为止

手机助手的标准行为是"唤醒一次、连续对话"，而不是每句话都得重新喊一次
唤醒词。命中后前端进入会话循环（新增 `phase = "conversation"`）：

```
命中唤醒词 → VAD 采集 → 拿到文本 → 发对话 → 等回答播完 → 自动再听下一句
                                                  ↑                    │
                                                  └────────────────────┘
                                        连续 2 轮没人说话 → 退出，回到待唤醒
```

其中"回答播完"的判定必须跨过**合成空档**：流结束到 TTS 起播之间有
200–800 毫秒，只看 `isPlaying` 会在空档里误开麦，把上一句的尾音录进去。
因此要求"连续 1.2 秒既不忙也不播"才算真的说完，播完再留 600 毫秒尾音缓冲
（内置麦离扬声器太近）。会话中途再喊一次唤醒词不会重入第二个循环，只做
打断播报，循环会在播报停下的那一刻自然接上。

唤醒开关默认开启（`localStorage` 键 `jarvis.wake`）：唤醒是贾维斯的主入口，
不该要求用户每次先去点一下开关；关掉过就记住用户的选择。

### 3.4 打包（`server/backend.spec`）

显式收集原生动态库、内置关键词资源目录、中文参数与自训练关键词模型，并补足子模块的显式导入。

> 注意：`pvporcupine` 的工具模块顶层依赖 `requests`，打包排除项里**不能**把它排除掉。

| 正样本 | 同上（SAPI 合成「你好贾维斯」） | **命中**。TTS 音色与真人有差距，只做存在性断言：合成音都认不出，真人更没戏 |
| 单元测试 | `pytest tests/test_wakeword.py` | 39 项通过；后端全量 446 项通过 |
| VAD 空闲路径 | `record/start {"vad":true,"leading_ms":3000}` + `stop` | 3.4 秒后返回 `idle:true`，安静退出不报错 |
| VAD 说话路径 | SAPI 播放 3.38 秒语音后 `stop` | 4.0 秒自动停录并转写出「今天天氣怎麼樣」——说完即走，不再等满 4 秒窗口 |

两个必须记住的 API 事实（都是真机才暴露的）：

1. `KeywordSpotter` **没有** `reset()`，清流用的是 `reset_stream(stream)`。
   单测替身若自造一个 `reset()` 就能跑通，真机一命中就 `AttributeError` ——
   这次正是这么发现的，替身已改名为 `reset_stream`。
2. `KeywordSpotter` 没有 `keywords` 属性，构造成功本身就是唯一信号，别去读它。

另外，模型压缩包里的文件名带训练配置后缀
（`encoder-epoch-99-avg-1-chunk-16-left-64.int8.onnx`），所以**任何地方都不能
写死文件名**，一律用 glob 且 int8 优先（`_sherpa_file`、下载脚本、验证脚本三处
保持一致）。
